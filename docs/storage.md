# Файлы, резервные копии и очистка истории

Оригиналы новых импортируемых Excel/ODS хранятся в приватном S3 под `uploads/<user-id>/<sha256>`. `uploaded_files` содержит имя, тип, размер, SHA-256, назначение и автора. Загрузка оригинала и запись метаданных предшествуют изменению рабочих данных; отказ S3 блокирует импорт. Неуспешная попытка импорта может оставить архив оригинала. Повторная загрузка сохраняет тот же объект и новую запись попытки. Анализ файла без импорта оригинал не архивирует.

Существующие оригиналы нельзя восстановить из разобранных строк PostgreSQL: для архива их нужно загрузить заново. Новые фотографии OCR сохраняются локально вместе с очередью отправки, привязанной к автору и снимку. При наличии связи оригинал отправляется в S3; повтор — при открытии раздела, восстановлении связи и каждые 30 секунд. Отправляются ожидающие фото всех снимков текущего автора, в том числе после импорта новой доски. Чужие фото автоматически не отправляются; сервер дополнительно сверяет автора с сессией. Старые локальные фотографии без записи в очереди автоматически не загружаются. Удаление локальной OCR-карточки отменяет ожидающую отправку, но не прерывает уже начавшуюся и не удаляет сохраненный архив. При выключенном S3 локальная очередь считается обработанной без серверного архива.

## Настройка

Переменные перечислены в `.env.example`. В Railway приложение использует ссылки на бакет `spider-viewer-storage`: `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION`. Включить архивирование: `S3_UPLOADS_ENABLED=true`. Локально оно по умолчанию выключено; бэкапы всегда требуют настроенного S3.

`S3_BACKUP_PREFIX=backups/production/` изолирует резервные копии окружения. Для тестов используется только `backups/storage-test/`. Railway требует virtual-hosted адресации: Bun получает полный адрес с именем бакета. Для S3-реализации с path-style установите `S3_FORCE_PATH_STYLE=true`.

## Бэкапы

`bun run db:backup` выполняет `pg_dump` в custom-format, загружает dump, скачивает его обратно и сравнивает SHA-256. После проверки сохраняется JSON-манифест. Только затем удаляются dump и манифесты старше `DB_BACKUP_RETENTION_DAYS` (по умолчанию 30 дней) в выбранном префиксе. `uploads/` retention не затрагивает. Локально нужно свободное место примерно для двух dump; таймаут pg_dump — 30 минут. PostgreSQL-клиент должен быть не старше сервера; production PostgreSQL 18, контейнеры включают клиент 18.

Отдельный Railway-сервис `spider-viewer-backups` запускается ежедневно в `00:00 UTC` / `03:00 Europe/Moscow`, завершает процесс после бэкапа, restart policy NEVER. Он получает DATABASE_URL через ссылку на Postgres-iUyM и S3 через ссылки на собственный бакет приложения. Сервис не запускает predeploy приложения и не меняет схему.

`Dockerfile.backup` — самостоятельный образ. При ручной загрузке отдельного build context положите его как `Dockerfile`, а `scripts/backup-db.ts` и `scripts/storage.ts` — в `scripts/`. В Railway cron и restart policy заданы настройками сервиса через API; его source не связан с GitHub, обновление скриптов требует повторной загрузки этого build context. API Railway уже запрещает установку нового configFile (поддержка существующих файлов объявлена до 2026-12-01). Миграция существующего приложения с `railway.json` на Railway IaC — отдельная задача.

Ручной запуск: `bun run db:backup` в окружении с доступом к PostgreSQL и S3 либо Run now у cron-сервиса Railway. Не выводите значения переменных и полные логи БД в отчеты. Проверяйте успешное завершение плановых запусков; существование расписания само по себе не подтверждает последующие бэкапы.

## Восстановление

1. Выберите ключ `.dump` в `backups/production/` и скачайте с проверкой: `bun run db:download-backup <key> .private/database.dump`. Каталог должен быть закрыт от постороннего доступа. Команда откажет, если файл уже существует или SHA-256 не совпал.
2. Создайте **новую пустую PostgreSQL**. Задайте стандартные `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD` для нее и выполните `pg_restore --exit-on-error --no-owner --no-acl --dbname=spider_restore_test .private/database.dump` (замените имя на целевое). Не восстанавливайте поверх рабочей БД. Бэкап всей БД содержит пользователей и хеши паролей и требует такого же контроля доступа, как сама БД.
3. Проверьте таблицы, количество записей, прогресс и вход в приложение. Затем переключите DATABASE_URL приложения на восстановленную БД. Файлы остаются в S3: dump содержит метаданные и ключи, а не байты объектов.

## Очистка истории за все время

Сначала `bun run db:clear-history`: выводит количества записей без удаления и без бэкапа.

Для выполнения остановите все экземпляры приложения и другие источники записи, дождитесь завершения запросов. Это необходимо также для исключения поздней записи старых событий в Redis. Запустите скрипт из отдельного административного окружения с DATABASE_URL, REDIS_URL (если приложение использует Redis) и S3:

```sh
bun run db:clear-history --execute --maintenance-confirmed
```

Скрипт блокирует запись таблиц `public`, экспортирует согласованный snapshot, сохраняет и проверяет S3-бэкап, затем в одной транзакции удаляет `change_audit_logs`, `cable_change_audit_logs`, `task_events`, замечания типов `room_change`/`cable_change`, связи и уведомления этих замечаний. Таймаут ожидания блокировки — 15 секунд. Длительность блокировки включает выгрузку и проверку бэкапа. Ошибка бэкапа или SQL до commit сохраняет историю.

Сохраняются пользователи, снимки, кабели, текущий прогресс (в том числе `cable_progress`), списки, позиции, комментарии, замечания к спискам/кабелям и ожидающие офлайн-изменения. Отмена старого перехода Kanban после удаления его события недоступна. Повторное выполнение допустимо; создаст новый бэкап даже при пустой истории.

После commit удаляются только `spider-viewer:audit` и `spider-viewer:audit:backdated` из Redis. Если это не удалось, команда возвращает ошибку и явно сообщает, что PostgreSQL уже очищен; выполните `bun run db:clear-audit-cache` до возобновления приложения. Сбой или остановка процесса между commit и Redis также требует повторной очистки кэша. Затем возобновите приложение: новые действия формируют новую историю.

Бэкапы содержат прежнюю историю до истечения срока хранения. Очистка не удаляет S3-оригиналы и не обещает физическое стирание данных с носителя PostgreSQL.
