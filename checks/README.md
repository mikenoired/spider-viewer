# Подключение исполняемых проверок

Это спецификация внедрения. В первой версии нет универсального исполняемого проверяющего скрипта, CI или настроенной защиты слияния. Наличие документа не блокирует ошибку.

## Реестр целевого проекта

Владелец и агент заполняют реестр в `docs/verification.md` целевого проекта. Не оставляйте фиктивные успешные команды вместо неподключенных инструментов.

| Поле                         | Требование                                                                   |
| ---------------------------- | ---------------------------------------------------------------------------- |
| ID и назначение              | Какой класс ошибки обнаруживает проверка                                     |
| Команда и рабочая директория | Точный воспроизводимый запуск                                                |
| Среда                        | Версии, установка из lock-файлов, необходимые сервисы, обезличенные фикстуры |
| Обязательность               | Для каких изменений и рисков требуется                                       |
| Условие успеха               | Код выхода и семантика; отсутствие тестов и пропуски учитываются явно        |
| Связанные AC/контракты       | Что подтверждается, что остается за границей                                 |
| Артефакт                     | Где сохраняется результат и как связан с состоянием исходников               |
| Владелец                     | Кто меняет правило и принимает исключения                                    |

Типичные группы: сборка/типы, статический анализ, поведение компонентов, интеграции, контракты, миграции, безопасность, свойства алгоритмов. Подключайте применимые группы, не симулируйте наличие остальных.

## Семантика исполнения

1. Ошибка обязательной команды означает неуспех. Не скрывайте код выхода через обработку ошибок, конвейер или безусловное продолжение.
2. Отсутствующая команда, недоступный сервис, пропущенный обязательный набор и таймаут дают статус «не подтверждено»; приемка блокируется до решения по политике проекта.
3. Проверяйте именно предъявляемое состояние, включая изменения конфигурации и зависимостей. Сохраните идентификатор запуска и исходников.
4. Нестабильный тест требует диагностики. Повтор до первого успеха не доказывает устранение причины.
5. Изменение теста, эталона или обязательности проверки требует собственного основания и отдельного внимания при ревью.
6. Документируйте ограничения: например, тест с заменителем сервиса не подтверждает реальную совместимость с сервисом.

## Внешние настройки

Владелец репозитория определяет обязательные проверки и ревью; ограничивает прямую запись и обход слияния; защищает изменения CI, правил и эталонов через возможности своей платформы и права доступа. Права агента должны соответствовать разрешенной работе. Независимый проверяющий процесс не должен зависеть только от утверждения агента об успехе.

Конкретные настройки зависят от платформы. Не включайте публикацию или деплой автоматически только потому, что локальные проверки прошли.

## Приемка подключения

- Из чистого окружения воспроизводится сборка и согласованный набор проверок.
- Заведомо неправильное поведение дает провал соответствующей проверки.
- Пропуск или недоступность обязательной проверки не превращаются в зеленый итог.
- Намеренно сломанная ветка не может быть принята обычным путем слияния.
- Защита изменений самих правил проверена владельцем; возможные обходы раскрыты.
- Артефакты не содержат секретов и позволяют установить состояние проверенного кода.

До выполнения этих условий записывайте статус внедрения «технические барьеры не подтверждены».
