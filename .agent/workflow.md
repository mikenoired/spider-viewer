# Рабочий цикл

## 1. Исходное состояние

Прочитай точку входа и применимые локальные инструкции. Проверь рабочее дерево, базу сравнения, среду, команды проверки и доступные источники требований. В Git зафиксируй commit и состояние незакоммиченных изменений. Без Git укажи способ идентификации снимка файлов.

При первом входе выполни обследование по `templates/project-context.md`. Для существующего контекста проверь актуальность затронутых сведений. Получи исходные результаты релевантных проверок; если это невозможно, зафиксируй ограничение.

**Переход:** известны рабочая область, исходное состояние и существенные пробелы. Неопределенность, блокирующая безопасный следующий шаг, разрешена либо этот шаг отложен.

## 2. Требования

Создай `tasks/<task-id>/task.md` по шаблону. Запиши цель, наблюдаемое поведение, границы и исключения. Дай критериям идентификаторы `AC-01`, `AC-02` и укажи источник ожидаемых результатов. Определи уровень риска.

Не добавляй требования, которые не следуют из задачи, контрактов или необходимых ограничений. При необходимости предложи уточнение и получи ответ владельца.

**Переход:** можно отличить правильный результат от неправильного; существенные неоднозначности не скрыты.

## 3. Потоки, входы и решение

Проследи затронутый путь: вход → валидация → преобразования/алгоритм → состояние/побочные эффекты → выход → потребитель. Укажи ссылки на реализацию, границы доверия, ошибки и возможные частичные результаты.

Заполни матрицу входов. Неприменимость категории обоснуй. Для алгоритма определи инварианты, допуски, единицы, точность и ограничения ресурсов, если это влияет на корректность.

Выбери минимальное решение, перечисли затронутые контракты и проверки. Для значимого архитектурного решения создай ADR по шаблону. Для повышенного риска определи независимое ревью и восстановление по политике проекта.

**Переход:** область влияния исследована достаточно для изменения; для каждого критерия определен способ проверки.

## 4. Реализация

Вноси небольшие связные изменения. Для дефекта сначала получи воспроизведение. Убедись, что падение проверки связано с дефектом, а не со сломанным окружением. Затем добейся прохождения и проверь регрессии.

Для новой функциональности используй короткие циклы проверки поведения. Не пиши тест, который лишь копирует тот же алгоритм и ту же ошибку. При изменении требований обнови карточку и оценку влияния до зависимой реализации.

**Переход:** ожидаемое поведение реализовано, локальные проверки дают объяснимые результаты.

## 5. Проверка и ревью

Выполни обязательный набор из `docs/verification.md`. Затем просмотри полный diff относительно зафиксированной базы, включая новые и незакоммиченные файлы. Проверка только commit-ов не покрывает рабочее дерево.

Проведи два отдельных прохода:

1. **Требования:** все AC выполнены; нет лишнего поведения; обработаны заявленные входы и отказы; сохранены необходимые контракты.
2. **Реализация:** простота, корректность алгоритма, зависимости, состояние, ресурсы, секреты, миграции, качество тестов и актуальность документации.

Для каждого замечания укажи место, последствие и способ подтверждения. Исправь блокирующие замечания. Если код изменился, повтори затронутые проверки. Саморевью не помечай независимым ревью.

**Переход:** обязательные проверки пройдены на финальном состоянии; обязательные ревью выполнены; нет неразрешенных блокирующих замечаний.

## 6. Завершение или передача

Заполни `completion.md`: состояние кода, связь AC с доказательствами, команды и результаты, ограничения, ревью и итоговый статус. Историю экспериментов сохраняй только когда она нужна для воспроизводимости или объяснения решения.

Если обязательство не выполнено, опиши точную границу готовности. Для продолжения другой сессией укажи текущую базу, изменения, неизвестные и следующий шаг. При возобновлении заново проверь состояние дерева и актуальность доказательств.

**Завершено:** только после выполнения условий статуса из `policies.md`. Деплой и слияние являются отдельными действиями и требуют разрешения в рамках проекта.
