# Spider Viewer

Средство для просмотра активности выполнения прокладки кабелей в РОАЭС

## Режим разработки

```bash
bun install # Установка зависимостей
cp .env.example .env # Создание файла с секретными ключами
# Меняйте значение JWT_SECRET на новое, например через комманду `openssl rand -hex 64`
# Задайте AUTH_SUPERUSERS_JSON с тремя суперпользователями в .env
docker compose up -d # Запуск базы данных
bun run db:push # Встраивание имеющейся схемы в БД
bun run auth:seed:superusers # Первичное создание 3 суперпользователей из AUTH_SUPERUSERS_JSON (только при пустой таблице users)
bun dev # Запуск проекта
```

Пользователей создаёт суперпользователь в разделе `/app/users`. Публичная регистрация доступна только для первого суперпользователя в пустой системе.

Суперпользователь может менять логины и пароли всех аккаунтов. Все пользователи могут сменить собственный пароль через меню аккаунта, указав текущий пароль. После изменения логина или пароля прежние сессии отзываются; при изменении своих данных потребуется повторный вход.

Удалять аккаунты может только суперпользователь; удаление аккаунтов с ролью `super-admin` запрещено. Удаление логическое: вход блокируется, аккаунт исключается из управления и выбора исполнителей, история работ сохраняется. Логин остаётся занят. Скрипты первичного создания суперпользователей пропускают непустую таблицу `users`, поэтому деплой сохраняет изменённые учётные данные.

Интеграционные проверки аккаунтов запускаются с отдельной тестовой PostgreSQL: `AUTH_TEST_DATABASE_URL=postgresql://... bun run test`. Они создают и удаляют изолированную схему; без этой переменной интеграционные тесты пропускаются. База приложения из `DATABASE_URL` для этих проверок не используется.

## Кабели, импорт и Kanban

Генеральная кабельная база хранится в `cables`. Каждая кабельная нитка имеет стабильный ключ: в приоритете пара «журнал + номер», при её отсутствии — нормализованные «марка + откуда + куда». Импорт карты демонтажа дополняет эту базу и связывает строки снимка с уже существующим кабелем, не создавая дублей.

В разделе карты доступен пошаговый импорт рабочего списка: файл сначала анализируется, затем показываются найденные, отсутствующие и неоднозначные позиции. Импорт обновляет только явно переданный прогресс, пустые ячейки не затирают состояние кабеля. Повторная загрузка того же файла возвращает исходную карточку, а не создаёт дубликат.

Маркировка кабеля хранится отдельно от описания с типом и сечением. При отсутствии точного ключа список сопоставляется по маркировке, а помещения помогают выбрать кабель среди нескольких кандидатов. Расхождения журнала, номера, маркировки или помещений показываются вместе с найденным кабелем и не блокируют импорт. Листы с колонками кабелей, но без журнала, номера или направления пропускаются с уведомлением. После обновления схемы недостающие маркировки и помещения генеральной базы восстанавливаются из исходных строк сохранённых снимков при первом обращении к базе.

Kanban отображается всегда и хранит карточки списков независимо от активного файла карты. Этапы: «Список сформирован», «Список в работе», «На проверку куратору», «Список в наладке», «Список выполнен». Карточка связана с кабелями через `cable_list_items`, содержит ответственного, комментарии, адресные замечания, уведомления и серверную историю действий.

Подразделения задаются при создании пользователя: ТАИ, СКМ/монтаж, наладка и куратор. MASTER (супер-администратор) выбирает любой этап; ТАИ — этапы передачи и проверки; наладка — этап наладки. Переходы дополнительно проверяются сервером: СКМ принимает задачу и становится ответственным, отмечает позиции и передаёт её на проверку; ТАИ/куратор подтверждает весь список для наладки или разделяет его. При разделении принятые позиции уходят дочерней карточкой в наладку, возвращённые остаются у СКМ — копии кабелей в генеральной базе не создаются.

Карточка имеет приоритет, плановую дату, номер и ссылку на исходную карточку. Замечание можно прикрепить к списку, одной, нескольким или всем позициям; связи с кабелями сохраняются в `remark_cable_items`. Все действия, включая отметки позиций, разделение и административную отмену перехода, записываются в `task_events`. Для демонстрации супер-администратор может нажать «Создать 3 демонстрационных списка»: будут созданы «Первый приоритет», «Второй приоритет» и «Третий приоритет» по 20 кабелей в первом столбце. Кнопка идемпотентна.

Сохранение прогресса карты не зависит от Redis: PostgreSQL фиксируется сначала, а обновление Redis-кэша ограничено коротким таймаутом. При сетевой ошибке форма сохраняет изменения и показывает ошибку, повторное нажатие не запускает второй запрос.

## Railway

Деплой настроен через `Dockerfile` и `railway.json`. Railway должен собирать сервис из корня репозитория и запускать контейнер командой из Dockerfile.

Обязательные переменные сервиса:

```bash
DATABASE_URL=postgresql://...
JWT_SECRET=...
AUTH_SUPERUSERS_JSON=[{"login":"supervisor-1","password":"ChangeMe123!"},{"login":"supervisor-2","password":"ChangeMe456!"},{"login":"supervisor-3","password":"ChangeMe789!"}]
AUTH_COOKIE_SECURE=true
```

Опциональные переменные:

```bash
REDIS_URL=redis://...
HEALTHCHECK_REDIS_REQUIRED=false
SHUTDOWN_TIMEOUT_MS=30000
```

Перед запуском контейнера Railway выполняет `bun ./scripts/predeploy.mjs`: он синхронизирует схему, затем создаются или обновляются 3 суперпользователя из `AUTH_SUPERUSERS_JSON`. Локально для версии схемы также доступна миграция `bun run db:migrate`. Healthcheck смотрит на `/healthz`, чтобы деплой не зависел от прогрева базы или Redis.
