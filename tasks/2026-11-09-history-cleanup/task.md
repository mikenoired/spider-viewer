# Очистка production-истории после проверки Redis

Статус: завершено.

Основание: прямой запрос владельца «запусти очистку истории; перед этим убедись, что у нас есть сервис redis в railway». Риск повышенный: разрешенное удаление production-истории. Код не меняется; исходники f4d1086cccddc9ecdc1141813bec019173a43e98, исходное дерево чистое. Поведение и процедура установлены в docs/storage.md и scripts/clear-history.ts, ранее проверены PostgreSQL/S3/Redis-интеграциями и восстановлением 24 таблиц.

## Критерии

| ID    | Ожидаемое поведение и проверка                                                                                                                     |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC-01 | Redis существует, активен, отвечает PONG; приложение получает ссылку REDIS_URL на этот сервис                                                      |
| AC-02 | Перед удалением остановлены все экземпляры приложения, проверено отсутствие других писателей; создан согласованный pg_dump в S3 и проверен SHA-256 |
| AC-03 | История прогресса, события Kanban и связанные замечания очищены; сохраняемые данные совпадают по количеству и хешам строк до/после                 |
| AC-04 | Только два audit-ключа Redis удалены; приложение возобновлено с исходным образом и подключенным Redis, health/readiness 200                        |

## Поток и границы

Railway API → проверка существующего Redis/переменных → PING → REDIS_URL через Railway reference → остановка deployment приложения → read-only контроль PostgreSQL → штатный скрипт clear-history (публичный адрес той же БД, pg_dump 18, экспортированный snapshot, S3) → удаление Redis audit-ключей внутри Redis-сервиса → read-only контроль → redeploy прежнего образа → health/readiness и PING из приложения.

Полные таблицы удаления: change_audit_logs, cable_change_audit_logs, task_events. Частичное удаление: remarks типов room_change/cable_change и их связи/уведомления. Остальные данные, S3 uploads и исходники не меняются. Сервис Redis уже есть в production, но REDIS_URL приложения до операции отсутствует. Другие сервисы проекта не останавливаются и их данные не очищаются.

## Сценарии и восстановление

- Redis не отвечает: очистку не начинать, устранить доступность.
- Неверная БД/образ или активные сторонние писатели: очистку не начинать.
- Ошибка backup/SQL до commit: штатный rollback; возобновить приложение без удаления.
- Ошибка Redis после commit: повторить DEL двух ключей перед возобновлением приложения.
- Несовпадение сохраняемых данных: не возобновлять запись; проверить восстановление свежего dump в новую БД и выбрать восстановление.
- Пустая история/повтор: штатный скрипт идемпотентен; без причины не повторять выполненное удаление.
- Большая БД: потоковый pg_dump во временные файлы, SHA-256 после повторного скачивания, ограничение pg_dump 30 минут.

Источник ожидаемого результата — разрешенная владельцем область удаления и неизменность всего дополнения к ней, проверяемая независимыми SQL-агрегатами. Независимое ревью — проверка runbook/области до выполнения; основной код уже независимо проверен в предыдущей задаче. При отсутствии прикладного diff повтор сборки/типов не проверяет операцию; применяются реальные read-only проверки сервисов и данных. Секреты, содержимое строк и dump не включаются в артефакты.
