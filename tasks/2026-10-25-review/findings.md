## F-01 [P1] Проверяйте сессию внутри функций чтения — src/lib/cable-map/functions.ts:26

`getDashboardData` и `getInstallationDashboardData` вызывают запросы без requireSession; то же у `getInstallationBoardData` в `src/lib/installation/functions.ts:22`. Проверка `/app` beforeLoad относится к навигации, а createServerFn доступна отдельным HTTP-вызовом. Неавторизованный вызов обходит страницу входа и получает кабели, помещения, списки, исполнителей; монтажная доска дополнительно возвращает пользовательские pending-изменения. Глобального серверного auth-middleware в проекте не обнаружено. Нужен guard непосредственно на этих серверных границах.

## F-02 [P1] Разбейте вставку генеральных кабелей на порции — src/lib/cable-map/import.server.ts:930

`canonicalCableRows` вставляется одним запросом, хотя строки снимка ниже уже разбиты по 500. При 26 000 уникальных кабелей компиляция Drizzle дает 234 000 параметров; установленный `postgres/src/connection.js:186` отклоняет >=65 534. Импорт падает и откатывает транзакцию. Аналогичный непорционный insert есть в `ensureCanonicalCableBase`:264; первый backfill старой большой базы также не проходит. Подтверждено компиляцией реального SQL без соединения с БД.

## F-03 [P1] Ограничьте целевой этап для наладки — src/lib/cable-map/task-workflow.server.ts:640

Ветка `move` проверяет только department=commissioning и текущий adjustment. Валидатор допускает произвольный status, а transitionTarget принимает его без дополнительной проверки. Поэтому обычный пользователь наладки может HTTP-запросом вернуть карточку в formed/in_progress/curator_review, хотя интерфейс дает только «Завершить наладку». Воспроизведен успешный adjustment → formed с обычной сессией commissioning. Требуется серверное ограничение целевого перехода.

## F-04 [P2] Читайте исходный прогресс из того же источника, что и карта — src/lib/cable-map/history.server.ts:201

Dashboard использует `coalesce(cables.progress, cableProgress.progress, 0)`, но сохранение берет oldProgress только из cable_progress. После импорта рабочего списка или повторного импорта карты генеральный прогресс может быть 80%, а запись снимка отсутствовать. Сброс 80 → 0 тогда считается отсутствием изменений: changedCount=0, запись не выполняется, UI показывает успешное сохранение. Для других значений история также фиксирует неверное старое значение. Воспроизведение подтверждает пропуск записи и отсутствие запроса генерального прогресса.

## F-05 [P2] Сравнивайте ревизию атомарно в UPDATE — src/lib/installation/mutations.server.ts:73

Проверка baseRevision выполняется отдельным SELECT до UPDATE, чей WHERE содержит только id. Два запроса с одной ревизией успевают пройти проверку и оба сохраняются; последний затирает первый без сообщения о конфликте. Это достижимо между пользователями и быстрыми переключениями одного Switch, который не блокируется на время запроса. DB double воспроизводит два успешных ответа revision=2 и 3 при baseRevision=1. Добавьте сравнение ревизии к UPDATE и проверяйте отсутствие обновленной строки.

## F-06 [P2] Защитите принятие Kanban-карточки от гонки — src/lib/cable-map/task-workflow.server.ts:702

Два сотрудника СКМ могут одновременно прочитать formed, пройти canTransition(accept) и выполнить UPDATE по одному id. Оба получают успех и события принятия, но responsibleUserId остается у последнего; первый теряет права отмечать свои позиции. Переход должен условно обновлять ожидаемый статус в одной транзакции, отклоняя проигравший запрос. Текущие SELECT/UPDATE и запись события отдельно допускают эту гонку.

## F-07 [P2] Перепроверяйте конфликты при утверждении офлайн-изменений — src/lib/installation/mutations.server.ts:218

hasConflict/serverDone фиксируются при submit и затем не обновляются. Если после submit другой пользователь изменил KKS, доска все еще показывает старый serverDone и «без конфликта». applyPendingChange безусловно перезаписывает актуальное состояние, даже когда утверждающий не видел изменения. Требуется сверка текущего состояния/версии при чтении pending и атомарная проверка при применении; транзакция вокруг цикла не заменяет проверку актуальности.

## F-08 [P2] Фильтруйте офлайн-очередь по снимку — src/hooks/useInstallationBoard.ts:281

flush читает всю IndexedDB-очередь и передает ее с текущим snapshotId, игнорируя сохраненный snapshotId каждого изменения. После импорта нового набора старые UUID отсутствуют в текущем снимке, сервер отклоняет весь пакет «Не все KKS найдены». Очередь не очищается, и старые элементы блокируют синхронизацию новых, включая фото. Нужны отдельные пакеты по снимку и явная обработка устаревших записей без их молчаливого удаления.

## F-09 [P2] Сохраняйте изменение при сетевой ошибке online-запроса — src/hooks/useInstallationBoard.ts:274

Выбор online/offline опирается на navigator.onLine. Когда сеть недоступна при сохраненном флаге true либо пропала между проверкой и POST, catch только выводит ошибку и снова вызывает refresh; в outbox ничего не записывается. После перезагрузки отметка исчезает. Для заявленной офлайн-доски сетевой сбой должен сохранять локальное намерение с idempotency key; ошибки прав и валидации при этом нельзя автоматически отправлять на повтор.

## F-10 [P2] Изолируйте локальную очередь по пользователю — src/lib/installation/offline.ts:7

IndexedDB и outbox общие для origin, записи не содержат владельца. logout удаляет только cookie (`auth/server.ts`), а при входе другого редактора useInstallationBoard автоматически flush-ит сохраненную очередь. Изменения A отправляются с сессией B и сохраняются как userId/userLogin B в mutations.server. Это искажает авторство и позволяет другому аккаунту отправить чужой незавершенный пакет. Нужна привязка к пользователю с проверкой при отправке и определенная политика смены аккаунта.

## F-11 [P2] Ограничьте кэширование GET в Service Worker — public/sw.js:32

Service Worker кладет каждый успешный GET в общий кэш без TTL, лимита и исключения серверных функций. Вызовы истории/деталей с различными query-параметрами и статические assets старых сборок остаются навсегда; имя кэша постоянно, очистка при activate удаляет только другие имена. Рост Cache Storage приводит к лишней записи полных ответов и давлению на общую квоту origin, где хранятся также офлайн-очередь и фото. Нужны allowlist ресурсов, политика обновления/удаления и исключение приватных динамических ответов из общего кэша. Production-порог исчерпания не измерялся.

## F-12 [P2] Обновляйте импортированный прогресс пакетно — src/lib/cable-map/task-workflow.server.ts:586

Для каждой сопоставленной строки с прогрессом внутри транзакции выполняется отдельный `await tx.update(cables)`. N позиций дают N последовательных round trips; при 10 000 строках и 10 мс RTT только ожидание запросов занимает порядка 100 секунд, без учета парсинга/сборки ответа. Это расчет чувствительности, не измерение production. Пакетный UPDATE FROM VALUES порциями уменьшает число обращений и длительность удержания блокировок, сохраняя транзакцию.

## F-13 [P2] Показывайте независимые Kanban-списки в целях замечаний — src/lib/cable-map/remarks.server.ts:67

getRemarksData выбирает списки через INNER JOIN с активным installation-снимком. Новый importCableTaskListFromFormData не устанавливает snapshotId: карточки по README существуют независимо от активной карты. В результате новые списки отсутствуют в выборе целей на `/app/remarks`; замечания по ним получают «Исходная запись недоступна», хотя карточка существует. Нужен запрос актуальных списков без обязательной привязки к снимку и разрешение их подписей.

## F-14 [P2] Сбрасывайте неудачную инициализацию OCR worker — src/lib/installation-photo/ocr.ts:132

workerPromise сохраняет Promise от createOcrWorker навсегда. Однократный сетевой сбой загрузки языка/worker оставляет rejected Promise; следующие фотографии и повтор после восстановления сети немедленно завершаются той же ошибкой до перезагрузки страницы. ## Общая оценка и ограничения

Главные риски — обход серверной авторизации, невозможность больших импортов и потеря/неверная атрибуция изменений при рассогласовании состояния. Найдены две конкретные проблемы затрат ресурсов (F-11/F-12); фактическая скорость браузера, latency БД и размер heap не профилировались. Пример большого импорта отдельно воспроизведен на этапе компиляции SQL.

Штатные тесты не запустились из-за неполного node_modules: отсутствуют @types/bun и @happy-dom/global-registrator. Работа с реальной PostgreSQL, браузерный E2E и полный production build не подтверждены. DB doubles не доказывают интеграционное поведение или полноту транзакционных гарантий. Обследование не является исчерпывающим аудитом безопасности и всех строк кода; исходное приложение не исправлялось.
