# Спецификация: распознавание суточных заданий по прокладке кабеля

Статус: реализация и проверка по согласованным уточнениям владельца.

## Цель и основания

Пользователь предоставил пример суточных заданий и попросил научить Spider Viewer их распознавать. Одна способность: преобразовать сканированное задание в проверяемые строки кабелей. Создание нового самостоятельного модуля управления заданиями и изменение правил готовности без уточнения не входят в согласованный объём.

Исходное состояние: main, commit 4600c1a0efc70858dac5df861b2032514bf51158, чистое рабочее дерево до исследования. Источники: предоставленный PDF, README.md, docs/project.md, docs/domain.md, docs/architecture.md, docs/verification.md и перечисленные ниже модули приложения.

Проверенные факты о примере: 16 страниц, текстового слоя нет. Визуально просмотрены все страницы на контактных листах, подробно страницы 1, 7 и 14. Таблицы повернуты на 90 градусов, есть продолжения без заголовков и страницы с малым количеством строк. Присутствуют короткий и расширенный форматы таблиц, цветные выделения нескольких цветов, рукописные даты, плюсы и добавленная от руки строка. Владелец уточнил: цвета игнорировать, плюсы обозначают выполненные комнаты. Связь конкретного плюса со стороной/помещением и смысл дат пока не определены.

Риск повышенный: неверная маркировка, дата или интерпретация отметки может привязать работу к другому кабелю либо ошибочно изменить готовность.

## Предположения для согласования

- Поддерживаем PDF из нескольких страниц и фотографии таких заданий.
- Первичный результат — редактируемая таблица с просмотром исходного фрагмента, затем явное подтверждение пользователем.
- Цвета игнорировать. Плюсы обозначают выполненные комнаты, но не служат основанием автоматически помечать весь кабель выполненным.
- Распознавание печатных строк обязательно; рукописные плюсы и даты показывать как данные для проверки. Без подтверждённой привязки плюса к комнате прогресс не менять.
- Сопоставляем с генеральной кабельной базой, сохраняя отсутствующие и неоднозначные позиции для проверки. Не ограничиваем результат KKS активной монтажной доски.
- Рабочие сканы не отправляются во внешние AI-сервисы без отдельного основания; первоначальный вариант опирается на существующее локальное OCR.

## Ожидаемый результат

Строка содержит страницу и область источника, номер кабеля, полную маркировку/KKS, марку и сечение кабеля, обозначения откуда/куда и соответствующие ряды, длину, трассировку и номер барабана — если эти поля есть и читаются. Дополнительные поля расширенной формы сохраняются без выдумывания значений. Номера, маркировки и барабаны остаются строками с ведущими нулями; длина — метры, десятичная запятая допустима.

Рукописная дата и принадлежность даты группе строк требуют отдельного подтверждения. Нечитаемое поле остаётся пустым/помеченным, исходный фрагмент доступен. OCR-уверенность и степень уверенности сопоставления с базой показываются отдельно.

После проверки пользователь создаёт список кабелей Kanban. Исходный PDF/скан связан с созданной карточкой. Цвета не влияют на распознавание бизнес-смысла. Плюсы означают выполненные комнаты; создание списка само по себе не меняет готовность кабеля или комнаты. Интерпретация плюсов с записью прогресса — отдельное подтверждаемое действие после определения стороны/помещения.

## Область влияния и существующий поток

Сейчас: installation-photo-panel.tsx принимает image/* → useInstallationPhotoRecognition.ts проверяет изображение до 25 МБ → ocr.ts уменьшает длинную сторону до 1800 px и запускает Tesseract eng+rus с PSM 11 → recognition.ts ищет токены в активных KKS → пользователь применяет кандидатов к готовности монтажа. Фото сохраняется в IndexedDB и через очередь архивируется в S3.

Ограничения: PDF отвергается в клиентской и серверной валидации; HTML image не декодирует PDF. Текущий OCR не извлекает структуру таблицы, номер страницы, метаданные задания и неизвестные строки. Нормализация заменяет 0 на O, удаляет разделители, а индекс хранит один объект на нормализованное имя — этот механизм нельзя использовать как единственный идентификатор кабеля. Распознавание цвета ориентировано на жёлтый маркер, тогда как в образце другие цвета. Нынешнее применение кандидатов означает изменение готовности монтажа и не равно импорту суточного задания.

Планируемый контракт потока: файл → валидация и страницы → ориентация/изображение → OCR с координатами → строки таблицы → сопоставление с базой → ручная проверка → подтверждённое действие. Оригинал, источник строки, автор и подтверждение должны сохраняться в рамках уже принятых механизмов архива/истории. Детальная реализация и выбор PDF-декодера — после согласования спецификации.

## Стек, структура и стиль

React, TanStack Start, Bun >=1.4.4, TypeScript; Tesseract.js уже установлен. PostgreSQL, Redis, IndexedDB и S3 — существующая инфраструктура. PDF-декодер и необходимость новой зависимости ещё не определены.

Источники: src/lib/installation-photo/{ocr,recognition,shared,offline,uploads.server}.ts; src/hooks/useInstallationPhotoRecognition.ts; src/components/installation-photo/; src/lib/cable-map/task-workflow.server.ts. Новый код и тесты размещать рядом с соответствующей областью, документы — в этой директории. Не смешивать правила суточных заданий и отметку готовности в существующем обработчике фото.

Стиль проекта: встроенный bun fmt, oxlint, именованные типы и явные ошибки. Пример существующего контракта: `return { candidates, ocrText: result.data.text };`. Новые результаты должны аналогично иметь явные поля и происхождение, без неявного сохранения состояния.

## Уточнение владельца: загрузка по столбцам Kanban

Источник: ответы владельца 2026-11-11. Поддержать PDF и сканы-изображения для заказчика, монтажа и наладки. Каждый пользователь загружает только в свой столбец. Для нового распознанного списка сохранять оригинал как вложение, после проверки создавать карточку со связанными кабелями.

Привязка к действующим названиям: заказчик (tai) → formed / «Задачи заказчика»; монтаж (skm) → in_progress / «В монтаже»; наладка (commissioning) → adjustment / «Список в наладке». Новые загрузки не дают права перемещать карточки в обход текущего workflow. Для curator отдельный столбец не назначать без требования. Для новых PDF/изображений ограничение по подразделению действует независимо от скрытия кнопки и роли пользователя; особое исключение MASTER для загрузки не запрошено. Существующие административные переходы и Excel-контракт не расширять молча.

Факт текущего кода: getAllowedImportStages в src/lib/cable-map/task-workflow.server.ts разрешает super-admin все этапы, tai — formed и curator_review, commissioning — adjustment; skm не получает ни одного этапа импорта. Поэтому простого расширения accept недостаточно: новый контракт загрузки должен разрешить монтажу его столбец и проверять допустимый столбец на сервере. Проверку повторять непосредственно перед созданием карточки/привязкой вложения: клиентские department, stage, cardId, результат OCR и промежуточный анализ не являются источниками полномочий.

Дополнительные AC:

- AC-08: заказчик, монтаж и наладка могут загрузить PDF, JPEG и PNG в свой столбец. Сервер отклоняет попытку выбрать чужой столбец, подменить department/stage или привязать файл к чужому столбцу напрямую через API. Проверить все пары «подразделение × столбец»; неизвестное подразделение запрещено по умолчанию.
- AC-09: оригинал связан с карточкой, известны автор, имя, MIME, размер и checksum. Просмотр/скачивание требует действующей авторизации; приватные S3-ключи не становятся публичными URL. Невалидный файл, отказ архива или ошибка распознавания не создают готовую карточку с потерянным оригиналом.
- AC-10: если владелец подтвердит вложения к существующим карточкам, добавление вложения не создаёт новый список, не меняет состав/готовность кабелей и повторно проверяет текущий столбец карточки. При её перемещении между анализом и сохранением — отказ с предложением обновить карточку. Конкурентный переход и привязка должны иметь атомарную проверку.

Следующий этап после уточнения AC-10: технический план и проверяемые задачи в этой директории, затем реализация в рамках согласованных требований. Push и деплой новой функции отдельно не запрошены.

## Финальное уточнение владельца

Подтверждены оба сценария: создание списка после проверки и вложения к существующим карточкам. Добавление вложения не запускает распознавание/изменение состава автоматически. Ограничение своего столбца применяется к обоим сценариям PDF/сканов. Цвета не используются, плюсы обозначают выполненные комнаты, но запись прогресса по ним в эту итерацию не входит: нет однозначной привязки сторон к помещениям.

## План реализации и задачи

1. Общий контракт PDF/JPEG/PNG, строгая проверка сигнатур/лимитов, таблица прав своего столбца; регрессионные проверки неправильного формата и всех подразделений.
2. Браузерное декодирование PDF через PDF.js (новая runtime-зависимость нужна: установленные библиотеки PDF не декодируют); последовательное OCR страниц существующим Tesseract, ориентация и ручная проверка/редактирование строк до анализа. Не отправлять сканы стороннему API.
3. Переиспользовать анализ генеральной базы и создание Kanban-списка для проверенных строк скана с progress=null. Сохранять оригинал в S3 и привязывать его к карточке.
4. Добавление/список/скачивание вложений: существующие task_events хранят событие привязки с метаданными S3, без миграции схемы. Загрузка сначала проверяет текущий столбец, затем архивирует оригинал, затем в транзакции блокирует карточку и повторно проверяет столбец. Чтение — по действующей авторизации доски, без публичных S3 URL. Повторы checksum под блокировкой не создают дубли вложений.
5. Проверки pure parser/валидации и прав, UI flow и реальные OCR-изображения из предоставленного PDF; линтер, типы, тесты, сборка. Недоступную интеграцию БД/облака явно раскрыть. Самопроверка не независимое ревью. Реальный PDF не включать в репозиторий.

Архив вложений требует S3_UPLOADS_ENABLED=true; при отключённом архиве сообщить ошибку, не выдавать временную копию за сохранённое вложение. Разрешены файлы до 25 МБ, до 50 страниц PDF; распознавание последовательно, отображение ошибок отдельных страниц и ручное редактирование до подтверждения. Публикация и изменения рабочих данных не входят в текущую реализацию.

## Корректировка хранения при самопроверке

Связь вложения не хранится только в task_events: существующая clear-history удаляет события, сохраняя рабочие карточки. Переиспользуется реестр uploaded_files и уже принятая в проекте область purpose с идентификатором сущности. До фиксации purpose=kanban-pending:<attempt-uuid>; в транзакции под блокировкой карточки — kanban-attachment:<list-uuid>. Неуспешные попытки остаются приватным архивом, но не становятся вложениями. В task_events остаётся только аудит привязки. Чтение/скачивание проверяет наличие карточки; очистка журнала не уничтожает связь. Миграция схемы не требуется.

При создании нового списка монтажа автор автоматически назначается ответственным: иначе текущие контракты отметки позиций и передачи списка запрещают ему работать с самостоятельно созданной карточкой. Одновременное подтверждение одного скана сериализуется по checksum+столбец; повтор возвращает существующую карточку. Количество строк ограничивается до запуска schema-валидации, включая формирование ошибок.
