# Сброс рабочего состояния после уточнения объема очистки

Статус: завершено. Риск повышенный: разрешенный владельцем сброс прогресса и удаление рабочих записей.

Источник: владелец уточнил, что на сайте должны очиститься Kanban, общий прогресс, замечания и история. Проверка production показала: журналы действительно пусты; сохранены 3 списка, 1 замечание, 91 cable_progress, 4949 кабелей и 2 снимка. Причина — первоначальный скрипт намеренно очищал только историю. Это уточнение области операции, а не повтор SQL-очистки той же истории.

База f4d1086cccddc9ecdc1141813bec019173a43e98; сохраняются существующие изменения docs/storage.md и артефакты предыдущих операций. Новые карты/кабели/аккаунты не удаляются. Действующий Redis — только spider-viewer-redis, чужой Redis вне границ любых команд.

## Критерии

- AC-01: отдельный явный флаг --reset-work-state в существующем скрипте сбрасывает прогресс кабелей/помещений/монтажа и удаляет списки Kanban с позициями/комментариями, все замечания/историю/уведомления и ожидающие монтажные изменения. Обычная очистка истории сохраняет прежнее поведение.
- AC-02: аккаунты, импортированные карты и кабели, геометрия, исходные строки, метаданные оригиналов и объекты S3 сохраняются. Атрибуция старого прогресса очищается, монтажные ревизии увеличиваются, чтобы старые online-запросы не перезаписали сброс.
- AC-03: preview без записи; выполнение только с execute + maintenance-confirmed; новый согласованный S3-бэкап обязателен до изменения данных; ошибки до commit откатывают сброс.
- AC-04: в production после остановки писателей сброс выполнен; серверные запросы страниц возвращают пустой Kanban/замечания/историю и 0 общего прогресса; после возобновления health/readiness 200, сохраняемые данные проверены.

## Поток и источники

scripts/clear-history.ts → все public write locks → export snapshot → pg_dump/S3/SHA-256 → SQL одной транзакции → Redis audit keys. getActiveDashboardData в queries.server.ts вычисляет общий прогресс из cables/cable_progress; Kanban читает priority_room_lists. remarks.server.ts читает remarks. KKS использует is_done/revision. Поэтому удаление только audit не меняет эти разделы.

## Сценарии и проверки

Preview/пустое состояние/повтор, отказ backup, rollback, сохранность ссылок/карты/пользователей, очистка всех производных состояний, устаревшие монтажные ревизии, конкурирующие писатели и post-commit Redis failure. Источник ожиданий — уточнение владельца и реальные page-level queries, не копия SQL удаления. Регрессионная проверка должна падать на исходном режиме истории и проходить с новым флагом. Нужны реальная disposable PostgreSQL, lint/test/build/typecheck, независимое ревью и проверки production после нового бэкапа. Восстановление — из нового dump в новую БД.

Старые формы/офлайн-черновики браузера автоматически не удаляются серверным скриптом; после maintenance нужно заново загрузить страницы. Ранее закэшированный экран не является проверкой состояния сервера. Монтажная БД production сейчас пуста; сброс серверных pending исключает автоматическое применение прежних изменений.
