# S3, резервное копирование и очистка истории

Статус: завершено.

Основание: запрос владельца 2026-11-09 и апрув предложенного решения. База: `d8a0248d13776166f7d9904390000d22e5a3cf9f`, исходное дерево чистое. Bun 1.4.4. Риск повышенный: удаление данных и внешняя инфраструктура.

## Критерии приемки

| ID    | Поведение                                                                                                                                  | Проверка                                         |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------ |
| AC-01 | Отдельная команда показывает объем удаления; удаляет всю историю прогресса, события Kanban и замечания к изменениям только при явном флаге | PostgreSQL integration, повтор, rollback         |
| AC-02 | Текущий прогресс, пользователи, снимки, списки, комментарии и замечания к кабелям/спискам сохраняются                                      | Сравнение состояния тестовой БД                  |
| AC-03 | До удаления успешно создан бэкап в S3; ошибка бэкапа блокирует удаление; очищаются только два audit-ключа Redis                            | Отказы, восстановление dump, Redis               |
| AC-04 | Новые импортируемые таблицы и фото OCR архивируются в приватном S3, метаданные связаны с автором в БД                                      | S3 integration, импорт при отказе S3             |
| AC-05 | Ежедневный бэкап, срок 30 дней, инструкция восстановления                                                                                  | Railway config, реальный upload/download/restore |

## Область влияния и решение

Потоки: авторизованные server functions → парсеры workbook → архив оригинала → PostgreSQL → UI. `history.server.ts` пишет PostgreSQL, затем вспомогательные ключи Redis. `queries.server.ts` читает историю; `remarks.server.ts` связывает замечания с `room_change`/`cable_change`. `task_events` используется для истории и отмены перехода: после очистки старые переходы отменить нельзя. `cable_progress` — текущее состояние снимка, сохраняется.

Скрипт: preview → явное выполнение → блокировки записи таблиц на время согласованного pg_dump и удаления → экспорт snapshot → dump и S3 → удаление в транзакции → очистка Redis. Ошибка до commit откатывает удаление. Рабочие записи после commit являются новой историей. Бэкап содержит удаленную историю до истечения срока хранения.

Используется встроенный Bun S3Client, новых runtime-зависимостей не нужно. Метаданные оригиналов — отдельная таблица, файлы адресуются по SHA-256. S3 включается явно; частичная конфигурация считается ошибкой. Новые фото OCR архивируются через отдельную IndexedDB-очередь, разделенную по автору и снимку; ошибки сети сохраняют очередь. Сервер проверяет сессию, автора, снимок, MIME и размер до 25 МБ. Старые локальные фото автоматически не отправляются.

## Матрица сценариев

| Сценарий                            | Ожидаемый результат                                                               |
| ----------------------------------- | --------------------------------------------------------------------------------- |
| Непустая / пустая история, повтор   | Удаление выбранных таблиц / нулевой результат                                     |
| Нет execute, неверный флаг          | Только preview / отказ                                                            |
| Нет S3 или pg_dump, ошибка загрузки | Данные не удаляются                                                               |
| Большая БД                          | Dump через временный файл, без полной загрузки в память; место требуется на диске |
| Конкурентные изменения              | Блокировка записи, lock timeout; при конфликте отказ без удаления                 |
| Прерывание / ошибка SQL             | Транзакция откатывается; загруженный бэкап может сохраниться                      |
| Redis недоступен                    | Явный неуспех и указание частичного результата после commit                       |
| Старые оригиналы отсутствуют        | Не выдумываются; архивируются новые загрузки                                      |
| Разные окружения                    | Изолированные префиксы бэкапов; retention не затрагивает uploads                  |

## Проверки и неизвестные

Обязательны lint:check, test, build, PostgreSQL/S3 интеграции, восстановление и независимое ревью по `.agent/policies.md`. Эталон — утвержденные владельцем AC и сравнение сохраненных данных, а не копия алгоритма удаления. Восстановление выполняется в новую БД, затем переключением DATABASE_URL.

Railway: доступ подтвержден защищенно переданным токеном; CLI доступен через bunx без изменения зависимостей. Production PostgreSQL 18 и правильный сервис подтверждены; отдельные S3/cron созданы и проверены. Результаты — completion.md. Никакое удаление production не запрашивалось: создан и проверен инструмент для запуска владельцем.
